01코드는 그대로, 타입만 다시 생성Same consumer. Regenerated types.

개인 Apollo Federation 실험에서 Product.name: String!을 String으로 바꿨습니다. CatalogOnly와 CatalogCards는 모두 검증을 통과했습니다. null을 허용해도 필드를 조회하는 것 자체는 유효하기 때문입니다.

In a personal Apollo Federation lab, I changed Product.name: String! to String. Both CatalogOnly and CatalogCards still validated: allowing null does not make selecting the field invalid.

strict-name.ts · 고정한 소비자 파일Fixed consumer file

import type { CatalogOnlyQuery } from './CatalogOnly.generated.js';

type Product = NonNullable<CatalogOnlyQuery['products'][number]>;

export function productHeading(product: Product): string {
  return product.name.toUpperCase();
}

공식 GraphQL Code Generator로 다시 생성한 name의 타입은 string | null입니다. strict 설정의 실제 TypeScript 컴파일러는 다음 진단을 냈습니다.

Official GraphQL Code Generator now emits string | null for name. The real TypeScript compiler, with strict settings, reports:

strict-name.ts(6,10): error TS18047: 'product.name' is possibly 'null'.

별도 소비자에서 (product.name ?? 'Unnamed product').toUpperCase()로 null을 처리하면 컴파일됩니다. 이는 변경된 타입을 처리한다는 근거입니다. 대체 문구가 제품에 적절한지는 별도 판단입니다.

A separate consumer using (product.name ?? 'Unnamed product').toUpperCase() compiles. It handles the changed type; whether that fallback is right for the product is a separate decision.

02이전 타입으로 통과하면, 무엇을 확인한 걸까?What did the passing stale-type check cover?

타입을 다시 생성하지 않으면 같은 코드가 통과합니다. 컴파일러가 받은 타입에는 여전히 non-null 보장이 남아 있기 때문입니다. 보고서에서 후보 스키마와 타입 생성에 사용한 스키마를 대조하면 차이가 드러납니다.

Without regeneration, the same code compiles. The supplied types still carry the old non-null guarantee. Comparing the candidate schema with the schema used for generation exposes the gap.

컴파일 성공은 검사에 넣은 타입에 대한 결과입니다. 새 스키마가 타입에 반영됐는지도 확인해야 합니다.A passing compile covers the types you supplied. Check that those types represent the candidate schema.

enum 확장에서도 구분은 같습니다. PREORDER를 추가해도 쿼리는 유효하지만, IN_STOCK과 SOLD_OUT만 처리하고 assertNever로 누락을 검사하는 소비자는 새 타입으로 컴파일되지 않습니다.

The same distinction appears with enum expansion. Adding PREORDER keeps the query valid, but a consumer that handles only IN_STOCK and SOLD_OUT and checks the remainder with assertNever no longer compiles with regenerated types.

exhaustive-status.ts · 실제 컴파일러 진단Actual compiler diagnostic

exhaustive-status.ts(14,33): error TS2345: Argument of type '"PREORDER"' is not assignable to parameter of type 'never'.

따라서 쿼리 검증은 “이 스키마에서 요청할 수 있는가”를, 소비자 컴파일은 “이 타입을 기존 코드가 처리하는가”를 확인합니다. 둘 다 런타임 동작 전체를 보장하지는 않습니다.

Query validation checks whether the operation is valid against the schema. Consumer compilation checks whether existing code accepts the supplied types. Neither establishes complete runtime behavior.

03직접 확인할 수 있는 근거Evidence you can inspect

전체 실행은 8개 조건, 실제 컴파일 28회이며, 이 글은 그중 네 조건을 골랐습니다. 코드·쿼리·스키마는 개인 실험용입니다. 리졸버와 소비자 함수는 실행하지 않았으며, 회사나 실서비스의 성과를 주장하지 않습니다.

The full run contains 8 cases and 28 actual compilations; this note selects four cases. Code, queries and schemas are synthetic personal fixtures. Resolvers and consumer functions were not executed; these are not employer or production results.

조회하지 않는 필드 추가는 생성 타입을 바꾸지 않았습니다. futureProofEnums: true를 켜면 catch-all 타입이 추가되어 기존 enum 소비자가 스키마 변경 전부터 실패했습니다. 이는 생성 정책의 차이이며, 응답을 변환하는 런타임 디코더는 아닙니다.

An unselected additive field left generated types unchanged. With futureProofEnums: true, a catch-all type made the closed enum consumer fail even before a schema change. That is a generator-policy difference, not a runtime response decoder.

예제의 NonNullable은 제품이나 재고 정보 자체가 없는 경우를 호출부에서 처리한다고 전제합니다. 도구 실패나 예상 밖의 진단은 실험 실패로 처리합니다. 의도한 타입 오류를 관찰했을 때의 종료 코드 0은 배포 승인을 뜻하지 않습니다.

The fixtures use NonNullable, leaving absent product or availability handling to the caller. Tool failures and unexpected diagnostics fail the experiment. Exit 0 after observing deliberate type errors is not deployment approval.
